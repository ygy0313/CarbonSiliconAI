01

为什么要反过来做

现在的产品都以「痛点」为切口：外卖解决饿，剧本杀 App 解决组局，记账解决钱。 人被切成十几个账号，每个 App 只认识你的一个侧面。

现状

痛点 → 功能 → 用户

每个 App 都在抢你的时间，都在从零认识你。你填过一百次口味偏好，没有一次被第二个 App 用上。

反转

人 → 需求 → 服务

档案在你手里，服务围着档案转。同一个「胃不好」，外卖看得到，聚会 App 也看得到 —— 因为它们读的是同一份你。

前提

调用之后更懂你

这是唯一的硬条件。如果每次调用都不留痕，那它只是个套壳聚合器。所以整条闭环的重心是「回写」。

这条线最容易走错的地方：做成又一个「超级 App」。一旦开始在自己的界面上堆功能，就又回到了以痛点切口的路上。 正确的姿势是 —— 界面极薄，能力极厚，数据极私有。

03

分层架构

五层，每层只做一件事。控制器的唯一职责是把 HTTP 翻译成服务调用 —— 一旦有人在控制器里写业务判断，这层就废了。

客户端
MINIPROGRAM
执笔首页 说一句 方案详情 记录 档案 服务市场
接入层
HTTP / ROUTER
路由 输入校验 全局错误处理 结构化日志 + requestId CORS 显式来源 优雅停机
编排层
ORCHESTRATOR
意图识别 能力召回 依赖解析 DAG 分层并行执行 仲裁合并 方案组装
能力层
AGENTS × 7
今日膳食 今日节律 剧本杀选本 场地推荐 茶歇配套 天气体感 日程核对
服务层
DOMAIN
记录抽取 画像编译 记忆检索 + 衰减 核对回写 LLM 适配（可降级）
仓储层
STORE
Collection 接口 JSON 原子写 写队列串行化 损坏自愈

最关键的机制：needs / provides 声明式依赖

服务之间不互相调用，只声明「我需要什么、我产出什么」。编排器据此自动拼装依赖图 —— 新增一个服务（比如红酒配餐）只需注册一个文件，编排核心代码一行都不用改。

服务声明需要产出被哪个意图召回
今日膳食今日节律 · 天气 · 饮食档案菜品建议吃什么 / 喝什么
剧本杀选本日程 · 社交档案本单组个局
场地推荐日程场地组个局
茶歇配套饮食档案茶歇组合组个局
选酒今日节律酒款 + 醒酒温度送点什么 / 喝什么
记梦—意象 + 情绪 + 三幕骨架记个梦
今日节律—宜忌味道（被膳食调用）
天气体感—温度体感（被膳食调用）
日程核对—具体日期 + 冲突（被选本/场地调用）
一次「组局」的真实执行图：第 1 层日程核对 → 第 2 层选本 ‖ 场地 ‖ 茶歇 三路并行。 这个结构不是写死的，是 needs 推出来的。
