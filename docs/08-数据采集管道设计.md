# 08 · 数据采集管道设计（邮件 / 消息 / 会议录音 / 简历 / 代码）

> 状态：**设计稿（二期实施）** · 2026-10-26
> 目标：让 AI 足够了解你，成为并肩作战的战友——但每一条进入系统的数据都必须走同一条流水线：**选择性导入、过一遍即弃原文、可溯源、可撤销**。
> 关联：`docs/07`（隐私架构）、`domain/obsidian.js`（经验笔记格式）、`vaultsearch.service.js`（检索层）。

---

## 0. 总原则（与既有红线对齐）

| # | 原则 | 落点 |
|---|---|---|
| 1 | **原文永不直接入库**。采集器产出的是「候选」，用户或 Agent 确认后才沉淀 | 本文件 §3 |
| 2 | **原始素材过一遍即弃**：邮件正文、聊天记录、录音文件只在内存处理，不落盘、不进档案 | 沿用 check-input 对照片/录音的同款断言 |
| 3 | **沉淀物进 Obsidian vault**（明文、用户自持），不进起居注主库 | vault 是用户资产，起居注只做检索 |
| 4 | **读 vault 必须持 scope=vault 票据** | `security/grant.js` 已实现 |
| 5 | **每条沉淀可溯源到来源**（哪封邮件/哪次会议/哪个仓库） | evidence 结构沿用经验层 |

## 1. 五类采集源与接入方式

| 源 | 接入方式 | 提取目标 | 落 vault 的笔记类型 |
|---|---|---|---|
| 邮件 | IMAP 拉取（只读账号 / 专用转发地址），**发件人白名单 + 关键词过滤** | 决策、承诺、项目结论 | `decision-experience` / `source-digest` |
| 消息 | 企业微信/飞书 webhook 或手动粘贴；不做监听 | 同上 + 待办 | `decision-experience` / `todo` |
| 会议录音 | 上传 → ASR 转写 → 提取，**音频即转即弃** | 决定事项、分歧点、行动项 | `meeting-minutes` |
| 简历 / 个人文档 | 文件导入（PDF/MD），一次性解析 | 事实层 facts（经历、技能、偏好） | `profile-fact` |
| 代码 / 设计 | git 仓库只读 clone（指定分支/目录白名单）；设计稿导出 MD | 技术决策、架构取舍、复盘 | `decision-experience` |

> 关键取舍：**不做全量同步**。每类源先配「过滤器」（发件人/群/仓库路径/时间窗），只处理命中过滤器的条目。宁漏勿滥——知识库的信噪比决定 Agent 的判断质量。

## 2. 统一数据 Schema（采集事件 → 候选 → 沉淀）

```
CollectEvent                     # 一次采集事件（内存态，处理完即丢）
├─ source: email|message|audio|document|repo
├─ origin: { id, title, from, at }   # 来源定位信息（沉淀后保留此元数据，不含原文）
├─ raw: string|buffer               # 原文/音频，仅内存
└─ extracted: Candidate[]           # 提取产物

Candidate                         # 候选（可持久化，等确认）
├─ kind: decision|todo|fact|insight
├─ situation / action / outcome    # 对齐 decision-experience 笔记字段
├─ evidence: { source, originId, quote }   # 溯源：来源类型 + 定位 + 原话片段（≤80字）
├─ confidence                      # 提取置信度
└─ status: pending|accepted|rejected      # 用户选择性导入的闸门

Note（vault 内）                   # accepted 后写成 markdown 笔记，格式沿用 frontmatter 约定
```

**conflict 规则**：Candidate 与既有 facts/experiences 冲突时进 conflict 队列（红线 10），不自动覆盖。

## 3. 流水线（六步）

```
采集源(过滤器) → 提取(LLM, 失败降级null) → 候选队列(用户确认)
  → 沉淀(写 vault 笔记) → git push aliyun → ECS 15min 拉取 → 可检索/可参与经验仲裁
```

- **确认方式**：H5/小程序「收件箱」页批量确认；也可设「高置信度自动接受」（默认关，开了写审计）。
- **提取失败**：LLM 返回 null 时事件标记 `unprocessed` 存放 7 天等重试，不静默丢弃也不阻塞后续。

## 4. 隐私边界

1. 邮件凭据 / 仓库 token 只存服务端 env（如 `COLLECT_IMAP_PASS`），永不入库不外显。
2. Candidate 只存「定位信息 + 提取片段」，存原文上限 80 字引用（引用本身也过 `redactDeep()` 脱敏手机号/证件号）。
3. 录音文件与邮件全文：处理完即从内存丢弃，**不留副本**（与识图/录音输入端同一承诺，legal.js 无需改——但上线前补一份「数据采集」章节进隐私政策 v2026.12）。
4. 撤销：删 vault 笔记即删数据（检索层 TTL 60s 内生效）；主库侧只留审计日志（谁在何时确认过什么），不含内容。

## 5. 实施排期

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 二期 A | 手动粘贴采集（消息/文档）+ 候选队列 + 确认入 vault | 本文件 Schema |
| 二期 B | 会议录音：上传→ASR→纪要笔记（音频即弃） | asr.service 已有 |
| 二期 C | 邮件 IMAP + 过滤器 + 定时拉取 | 用户配专用邮箱 |
| 二期 D | 仓库只读采集（git log + diff 提取技术决策） | 无 |
| 远期 | 向量 RAG（替换 vaultsearch 内部实现，签名不变） | 嵌入模型 |

## 6. 与「战友关系」的连接

采集不是「喂档案」，是给执笔**反对你的证据**：沉淀的每条 `decision-experience` 都参与检索仲裁（validity×applied_count 重排序已上线）。当用户的主张和历史经验的 outcome 冲突时，执笔按人格约定直接摆出来——这是「发现 & 创造」的原料。
