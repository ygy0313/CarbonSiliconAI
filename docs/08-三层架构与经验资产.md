# 08 · 三层架构与经验资产

> 本轮重构回应的问题：产品不是「意识上传」，而是**用户经验的硅基化封装器**。
> Agent 是用户某个经验领域的数字分身；其他 Agent 是服务这个分身的工具层；
> 微信小程序 / H5 只是入口。经验必须可量化、可复用、可带走 —— 这才是「资产」。

## 1. 三层职责：谁主谁次

```
┌─ 第一层：用户专属 Agent（主）─────────────────────────┐
│  不是聊天机器人，是「经验资产」的持有者与经营者。      │
│  能力：记住 → 提炼 → 调用 → 用结果修正自己。          │
│  本仓库落点：person + silicon（人格包）+ experiences   │
├─ 第二层：服务型 Agent 集群（从）──────────────────────┤
│  节律 / 天气 / 日历 / 膳食 / 选酒 / 记梦 / 选本 / 场地 / 茶歇 ……    │
│  只接受调度（needs/provides 声明依赖），不拥有用户。   │
│  本仓库落点：agents/*，由 registry.resolvePlan 解析   │
├─ 第三层：入口（小程序 + H5）──────────────────────────┤
│  只做三件事：输入碎片、看到资产反馈、触发任务。        │
│  端上不算重逻辑、不存核心记忆。                        │
└───────────────────────────────────────────────────────┘
```

判断一个功能该放哪一层的标准：**这个数据离开这个用户还有没有意义。**
推荐规则（经验）离开用户毫无意义 → 第一层，按人隔离；
茶歇价格参考离开用户照样成立 → 第二层，全局共享。

## 2. 记忆分层：碳基 → 硅基的关键

「数字记忆」不能是一锅粥。三层各管一件事：

| 层 | 装什么 | 生命周期 | 本仓库落点 |
|---|---|---|---|
| **原始层** | 用户输入的原文（脱敏前），只追加不修改 | 永久（密文） | `episodes[].rawCipher`（AES-256-GCM 保险箱） |
| **结构化层** | 抽取后的实体与事件：「10 月，试了 X，结果 Y」 | 随事实半衰期衰减（90 天） | `facts`（可核对声明）+ `traits`（行为统计） |
| **经验层** | 可执行的判断规则：「在 T 情境下优先 X，N/M 次奏效」 | 随应用效果升降 | `experiences`（本轮新增） |

原始层保证「可恢复」，结构化层保证「可推理」，经验层保证「可复用」。
三层都带溯源链：经验 → 调用记录 → 记忆 → 原文密文，每一跳都能查。

## 3. 经验条目：资产的原子单位

```jsonc
{
  "rule": "在「胃敏感、微辣」这类情境下，优先「清汤面」——过去 4/5 次你都采纳了。",
  "trigger": { "tags": ["胃敏感", "微辣"], "scene": "solo", "intent": "eat" },
  "effectiveness": 0.74,        // 0-1，每次应用结果更新一次
  "applied": 5, "followed": 4,  // 被调用 / 奏效
  "status": "active",           // proposed → active → dormant/archived
  "evidence": [{ "refId": "inv_...", "kind": "invocation" }],  // 必须能溯源
  "solidified": false           // 反复奏效后固化为「技能」
}
```

四条硬规则（写在 `domain/experience.js`）：

1. **不能溯源的经验不许存在。** `createExperience` 收到空 evidence 直接拒收。
2. **评分渐进更新，不许突变。** 奏效 = 向 1 靠 18% 剩余距离；失效 = ×0.78。
   一条用 10 次建立的规则不会被一次意外打穿；反过来它也需要连续失效才会休眠。
3. **Agent 只能降权，不能删除。** 经验是用户的资产，沉下去可以，抹掉不行。
4. **双环约束：Agent 可自动改分数（单环），不可改「什么算有效」（双环）。**
   评估标准（固化线 / 休眠线 / 最小样本数）存在 `criteria`，带版本号，
   修改接口强制要求 `confirm: true`，改动进审计日志。

## 4. 经验学习循环（本仓库已跑通）

```
记录 ──→ 编排（检索 Top-K 经验参与仲裁）
  ↑              │
  │              ▼
  │        用户反馈（采纳/否决）
  │              │
  │              ▼
  └──反思 ←── 应用结果回写经验评分
（重复 ≥ minSupport 次的情境模式 → 候选经验）
```

关键设计：**经验必须影响结果，不能只当注解。**
反思产出的规则指向一个具体选项（如「拌汤」）；下次编排时若该选项出现在候选里，
会被提到第一位并标注「你以前在这类情境下选过它」。若只贴一张标签而不改变排序，
「经验资产」就是装饰品——这条在 `orchestrator.applyExperienceBoost` 里落地，
且只提升已存在的候选，不凭空造卡片（经验是判据，不是商品）。

验证闭环的方式只有一个：**用户是否在两周后回来查看自己的经验资产，
并在新情境中调用它。** 资产页的 `nextAction` 字段就是为这个行为设计的。

## 5. 隔离与不可迁移

- 每条经验都绑定 `personId`；按 id 读取必须带 personId，跨人访问返回 **404**，
  不是 403 —— 403 本身就泄漏了「这条经验存在」。
- 导出文件里，经验与评估标准一起带走（`qijuzhu/v1` 的 `experiences` / `criteria` 字段），
  恢复到新档案时 **id 重新生成**：数据可搬运，身份不复制。
- 每个 person 的 Agent 状态天然隔离（独立 JSON 文档），后续换 PostgreSQL 时
  这条红线不变：**所有查询必须带 personId 前缀，不做跨人索引。**

## 6. 后端语言决策：C++ 放哪、不放哪

### 6.1 先看实测数据（同一负载，同机对比）

| 经验条数 | C++ 内核 | JS 镜像（V8） | 差距 |
|---|---|---|---|
| 200（普通用户半年量） | 0.222 ms/次 | 0.292 ms/次 | **1.3×** |
| 1,000 | 1.219 ms/次 | 1.459 ms/次 | 1.2× |
| 5,000（重度/批处理） | 5.815 ms/次 | 7.809 ms/次 | 1.3× |
| 反思挖掘 2 万事件 | 3.5 ms | — | CPU 密集批处理 |

结论很清楚：**V8 在这类代码上只比 C++ 慢 25–30%，不是数量级差距。**
多用户场景下真正的延迟大头是 LLM 调用（秒级）和网络 IO，不是打分（毫秒级）。

### 6.2 所以：不整体重写，把内核抽出来

**全量 C++ 重写是负收益**：5,400 行已验证的 Node 代码重写要几周，
换来的全链路提速不足 1.3 倍，而且丢失 LLM 生态、JSON 处理、开发迭代速度。
正确的切法是按「计算密集 vs IO 密集」分：

```
┌──────────────────────────────────────────────┐
│  Node 网关（8787）                            │
│  路由 / 鉴权 / 脱敏 / 编排 / 存储 / 静态 H5    │  ← IO 密集，Node 最擅长
└──────────────┬───────────────────────────────┘
               │ localhost HTTP（协议稳定）
┌──────────────▼───────────────────────────────┐
│  C++ 计算内核（8788，core/，零外部依赖）       │
│  经验评分排序 / bigram 相似度 / 反思挖掘       │  ← CPU 密集
└──────────────────────────────────────────────┘
```

C++ 内核的真正价值不在今天的延迟，在于：

1. **把 CPU 密集的批处理移出 Node 事件循环。** Node 只有一个线程，
   「给 2 万条记录做反思挖掘」这种活会让所有请求卡住 —— 这必须挪出去。
2. **内核协议（`/v1/experience/rank`、`/v1/reflect/mine`）是稳定契约。**
   未来多用户性能优化时，可以独立对内核做水平扩展，Node 层一行不改。
3. **内核是纯函数、零外部依赖**（`make` 一行编译，可交叉编译到 ECS），
   自检 17 项、压测内置，随时能嵌到别的宿主。

### 6.3 降级红线

内核是加速器，不是依赖（与本仓库「LLM 可选」同一条红线）：
`server/src/core/fallback.js` 是算法逐项对齐的 JS 镜像，内核不可用时自动接管，
结果一致只是稍慢。实测：停掉内核后编排照跑，`engine=js`，1ms。
**两套实现互相为对方做测试** —— check-experience.js 的同构断言曾抓出
JS 镜像里 evidence 数组导致的 NaN bug，C++ 侧无此问题，对比立刻现形。

## 7. 现状与演进

**已落地（本仓库可运行）：**

- 经验层全套：schema、反思、检索、应用、回写、固化、休眠、资产盘点
- 双环约束：评估标准带版本号，改标准必须用户 confirm，进审计
- C++ 内核 + JS 镜像 + 同构测试 + 压测
- H5「经验」页：资产总览 / 分组管理 / 一键提炼 / 标准确认
- 导出格式升级：experiences + criteria 随档案带走，可恢复

**下一步（按优先级）：**

1. 微信 AI 开发模式（beta）内测开放后，把 `record_memory` / `query_experience`
   封装成 SKILL —— 当前用普通小程序 + 自建对话界面，不受内测政策影响。
2. 结构化层换 PostgreSQL（JSON 文件在单机 100 用户内没问题），
   经验检索若上量再考虑向量库 —— 当前 bigram 余弦在 5,000 条内够用且可解释。
3. 反思目前按固定周期跑，接入事件触发（反馈满 N 条自动跑）已做，
   定时全量重排（ECS cron）待接。
4. 经验的「技能封装」：把 solidified 的经验导出为可被其他 Agent 调用的
   独立 prompt 片段 —— 这是「经验交易」的前提，先不做，等产品验证后再说。
