# 硅基记忆体 · 整体架构设计

> 版本 v0.1 ｜ 2026-10-18 ｜ 对应可运行代码：`server/`、`miniprogram/`

## 一、一句话与核心命题

**一句话**：一个人就是一个 Agent。把个体的行为、判断、履历、记忆编译成可执行的「硅基体」，让所有 App / Agent / Skill 反过来围着这个人转。

**核心命题**：现在的产品都以「痛点」为切口——外卖解决饿，剧本杀 App 解决组局，记账解决钱。人以碎片的方式被切成十几个账号。我们要反过来：**以人为本体，需求从人身上长出来，服务被临时调用，用完即走。**

这件事成立的前提只有一个：**调用之后，人比调用前更被理解。** 所以整个架构的重心不是推荐算法，而是「记录 → 编译 → 调用 → 核对 → 回写」这条闭环。

## 二、概念模型

四个名词，务必定死，后面所有设计都从它们推出来：

| 概念 | 定义 | 不是什么 |
|---|---|---|
| **碳基档案 Carbon Profile** | 一个人的结构化快照：事实、记忆、倾向 | 不是用户画像标签，不是兴趣打分 |
| **硅基体 Silicon** | 由档案编译出的可执行人格包：我是谁 + 我记得什么 + 我偏好什么 + 我能调什么 | 不是一个聊天机器人，不是一段 system prompt |
| **生活服务 Agent** | 以痛点为切口的能力单元（App / Agent / Skill），声明自己能干什么、需要什么 | 不是被「打开」的页面，是被「调用」的函数 |
| **核对回路 Verification Loop** | 每次调用后的采纳/否决/修正，回流成档案的置信度变化 | 不是点赞，不是评分，是事实修订 |

关系：

```
        ┌──────────────────────────────────────────┐
        │            一个人（本体）                  │
        └──────────────────────────────────────────┘
                 │ 记录
                 ▼
        ┌──────────────────┐   编译    ┌──────────────────┐
        │   碳基档案        │ ────────▶ │    硅基体         │
        │ 事实/记忆/倾向    │ ◀──────── │ 人格包 + 能力白名单│
        └──────────────────┘   回写    └──────────────────┘
                 ▲                            │ 调用
                 │ 核对                        ▼
        ┌──────────────────┐         ┌──────────────────┐
        │    核对回路       │ ◀────── │   多服务编排      │
        └──────────────────┘  反馈    └──────────────────┘
                                              │
                          ┌───────────────────┼───────────────────┐
                          ▼                   ▼                   ▼
                    给您请安·膳食        剧本杀工坊·开本       本地生活·场地
```

### 档案的三层结构

| 层 | 内容 | 写入者 | 可信度 |
|---|---|---|---|
| **事实层 Facts** | 「辣度耐受 = 微辣」「常驻城市 = 银川」 | 用户自述 / 系统归纳 | 带置信度，会随时间衰减 |
| **记忆层 Episodes** | 「10 月 16 日晚上吃了辣糊糊，半夜胃烧」 | 用户记录（不可变） | 高，原始证据 |
| **倾向层 Traits** | 「夜里更活跃」「组局常客」「挑得比较细」 | 系统从记忆统计 | 中，需要被核对 |

关键区分：**事实是声明，记忆是证据，倾向是推断。** 三者的可信度不同，冲突时的处理方式也不同——事实冲突要问人，倾向错了只需调整权重。

## 三、关键设计决策

每个决策都写清「为什么不选另一条路」，因为架构的价值在于排除。

### 1. 服务用 needs/provides 声明依赖，而不是硬编码调用

```js
{
  id: 'meal.prepare',
  intents: ['eat'],                          // 什么时候被召回
  needs: ['context.fortune', 'context.weather', 'profile.diet'],  // 我需要什么
  provides: ['dishes'],                      // 我产出什么
  run: async (ctx) => ({ items: [...] })
}
```

编排器看到 `needs: context.fortune`，会自动把「今日节律」这个 agent 拉进执行计划。

**好处**：新增一个服务（比如「红酒配餐」）只需注册一个文件，声明它需要 `profile.diet` 和 `context.fortune`，编排器不用改一行代码。这是「链接已有 app / agent / skills」真正落地的地方——不是写 if-else 去判断调哪个，而是让依赖图自己长出来。

**替代方案**：在编排器里写死 `if (intent === 'eat') call(mealAgent)`。简单，但每加一个服务都要改核心代码，第三个月就会变成一坨。

### 2. LLM 是增强层，不是依赖层

规则引擎（词典 + 打分）承担全部主流程，LLM 只做两件锦上添花的事：补充抽取、润色表达。

任何一次 LLM 调用失败、超时、返回非法 JSON，都返回 `null` 让上层降级，**绝不阻断编排**。

**理由**：MVP 要 0 元跑通，且演示不能因为没配 key 就白屏。更重要的是——推荐结果要可复现、可解释。同一句话今天问和明天问，如果模型抽风给出完全不同的结果，用户就不会信任这个「记忆体」。

### 3. MVP 不做向量检索，用标签倒排 + 时间衰减

记忆检索的打分：

```
score = 标签命中数 × 0.35 + 场景匹配 × 0.2 + 近 60 天衰减加分
```

**理由**：单用户几百条记忆，标签倒排足够；向量库要么花钱（ embedding API ），要么本地跑模型（吃内存）。而标签方案最大的优势是**可解释**——能直接告诉用户「因为你在 10 月 16 日记录过胃不舒服」，这比「相似度 0.87」有说服力得多。

预留 `recall()` 接口，记忆量过万时替换实现即可。

### 4. 置信度会衰减，冲突不自动覆盖

事实的置信度按 90 天半衰期衰减，下限 0.15。新值与旧值冲突时不直接覆盖，而是进**冲突队列**等用户裁决：

```
「你的档案里写的是『微辣』，这次记录是『重辣』，以哪个为准？」
  → 改成重辣 / 保留微辣 / 都算，看情况
```

**理由**：「今天想吃辣」和「我平时吃辣」是两件事。自动覆盖会让档案在几次极端记录后失真，而频繁追问又会烦人——所以只有「两个值都足够可信且不一致」时才问。

### 5. 数据本地优先，JSON 文件起步

所有读写走 `Collection` 接口，当前实现是 JSON 文件 + 原子写 + 写队列串行化。

**理由**：0 成本、可 git 版本化、可直接打开看、迁移无痛。换 SQLite / Postgres 只替换 `store/db.js` 一个文件。

## 四、分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  客户端层  微信小程序                                          │
│  硅基体首页 / 说一句 / 方案 / 记录 / 档案 / 服务市场            │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP (JSON)
┌──────────────────────────▼──────────────────────────────────┐
│  接入层  index.js                                             │
│  路由 · 请求校验 · 全局错误处理 · 结构化日志 · CORS · 优雅停机   │
└──────────────────────────┬──────────────────────────────────┘
┌──────────────────────────▼──────────────────────────────────┐
│  编排层  orchestrator.service                                 │
│  意图识别 → 能力召回 → 依赖解析 → 分层并行 → 仲裁合并 → 落库     │
└───────┬──────────────────┬──────────────────┬───────────────┘
        │                  │                  │
┌───────▼──────┐  ┌────────▼───────┐  ┌───────▼──────────────┐
│ 能力层        │  │ 领域服务层      │  │ 记忆层                │
│ agents/*     │  │ extract        │  │ profile.service      │
│ 7 个服务      │  │ verify         │  │ 编译 / 检索 / 衰减     │
│ 声明 needs   │  │ 抽取 / 核对     │  │ traits 统计           │
└───────┬──────┘  └────────┬───────┘  └───────┬──────────────┘
        │                  │                  │
┌───────▼──────────────────▼──────────────────▼───────────────┐
│  仓储层  store/repos + store/db                               │
│  Collection 接口 · JSON 文件 · 原子写 · 写队列                  │
└─────────────────────────────────────────────────────────────┘
```

**约束**：控制器不写业务逻辑；服务层不依赖 HTTP 对象；agent 不互相调用（只声明依赖）。

## 五、数据模型

| 集合 | 关键字段 | 说明 |
|---|---|---|
| `persons` | id, name, city | 一个 person = 一个硅基体宿主 |
| `facts` | personId, key, value, confidence, source, evidenceEpisodeIds | 声明事实，带来源与证据链 |
| `episodes` | personId, ts, text, tags, entities, summary, kind | 行为记忆，不可变 |
| `traits` | 由 episodes 实时计算 | 不落库，避免不一致 |
| `invocations` | personId, input, intent, cardIds, trace, feedback | 每次编排的完整快照 |
| `conflicts` | personId, key, previous, incoming, status | 待裁决冲突 |

`episodes.kind` 取值：`note`（记录）、`adoption`（采纳）、`rejection`（否决）、`correction`（修正）。后三种是反馈信号，也进记忆——因为「他否决过这个」本身就是关于这个人的信息。

## 六、服务接入协议

一个服务就是一个文件，导出注册调用：

```js
registry.register({
  id: 'wine.pair',                 // 全局唯一
  service: '红酒推广',              // 归属的产品
  name: '配餐建议',
  intents: ['drink', 'gift'],      // 哪些意图能召回它
  needs: ['profile.diet'],         // 需要什么（编排器负责满足）
  provides: ['wine_pairing'],
  cost: 'free',
  run: async (ctx) => ({
    items: [{ id, kind, title, desc, why: [], evidence: [], score, source, meta }],
    meta: {}                        // 给下游 agent 消费的结构化输出
  })
})
```

`items[].kind` 决定它在结果里的位置：

| kind | 含义 | 展示 |
|---|---|---|
| `plan` | 多服务拼成的完整方案 | 金色卡片，置顶 |
| `primary` | 主推 | 绿色边框 |
| `option` | 备选 | 普通卡片 |
| `note` | 文化/解释性信息 | 灰色小字 |
| `context` | 环境参考（天气、日程） | 灰色小字 |

**每个 item 必须能回答「为什么是它」**：`why` 至少一条，`evidence` 尽量引用具体记忆。这是硬约束——不能溯源的推荐等于黑箱。

## 七、编排算法

```
输入：一句话 + 快捷标签
  │
  ├─① 意图识别：关键词加权，输出 type / confidence / matched
  │    命中词越多越确定；两个意图分数接近时置信度下调
  │
  ├─② 编译硅基体：facts（衰减后）+ 近期记忆 + traits + 表达风格
  │
  ├─③ 能力召回：intents 匹配 → 种子 agent 列表
  │
  ├─④ 依赖解析：递归展开 context.* 依赖 → 分层执行图（DAG）
  │    depth 大的先执行，同层并行
  │
  ├─⑤ 分层执行：每个 agent 4s 超时，失败隔离（不影响其他 agent）
  │
  ├─⑥ 仲裁合并：
  │    · context/note 沉底
  │    · primary > option
  │    · 标题归一化去重
  │    · gather 场景额外组装成「一个局」（本 + 场地 + 茶歇 + 时间线 + 待办）
  │
  └─⑦ 落库：invocation 存完整 trace，供复盘与调试
```

**分层执行的意义**：一次「组局」的真实执行图是

```
第 1 层：日程核对
第 2 层：剧本杀选本 ‖ 场地推荐 ‖ 茶歇配套   ← 三个并行
```

选本要依赖日程（判断 5 小时的本今天来不来得及），场地和茶歇并行。这套结构不是写死的，是 `needs` 推出来的。

**失败隔离**：某个 agent 挂掉，其余照常出结果，trace 里标红。宁可少一条建议，不能整页报错。

## 八、核对回路

三种信号，权重不同：

| 信号 | 触发 | 动作 | 权重 |
|---|---|---|---|
| **显式修正** | 用户点开档案改值 / 说「不对，我其实…」 | 直接改事实，confidence 0.95 | 最高 |
| **显式否决** | 点「不要这个」+ 选原因（太辣/太贵/不舒服） | 按原因映射到对应维度做调整 | 中 |
| **隐式采纳** | 点「就这个」 | 相关维度 +0.02，写入 adoption 记忆 | 低 |

否决原因到事实的映射是设计的重点：

```
太辣了      → diet.spicy 降一档（重辣→中辣→微辣→不吃辣）
太贵了      → life.budget × 0.85
吃了不舒服   → diet.stomach = 偏敏感
太远        → 不建事实，只记一条 rejection 记忆
就是不想     → 不建事实
```

**为什么这样设计**：用户不会主动维护档案。但「不要这个」是一个几乎零成本的动作——把它翻译成一次档案修订，档案就有了自维护能力。

## 九、演进路线

| 阶段 | 目标 | 关键动作 | 成本 |
|---|---|---|---|
| **MVP（当前）** | 单人自用跑通两条流程 | 7 个服务、规则引擎、JSON 存储 | 0 元 |
| **V1 内测** | 10-30 人真实使用 | 接 LLM 增强、多用户隔离、Postgres、HTTPS 域名 | < 100 元/月 |
| **V2 开放** | 第三方服务接入 | 能力市场、manifest 审核、按调用计费 | 随规模 |
| **V3 硅基体互联** | 多个硅基体互相协商 | 「我们俩都有空，帮我约他」——agent 对 agent | — |

V3 才是这个产品真正的想象力所在：现在的「约人」要靠微信来回问，未来是两个硅基体在后台对齐时间、预算、口味，只把结论给你。但那是数据密度足够之后的事，先别急。

## 十、已知边界与风险

| 风险 | 说明 | 当前应对 |
|---|---|---|
| **冷启动** | 前 10 条记录之前，硅基体毫无价值 | 用 12 个维度的问题清单快速建档；预置演示档案 |
| **录入成本** | 用户不愿天天写字 | 快捷标签、语音（待做）、拍照识食（可复用「给您请安」的 vision.js） |
| **推荐同质化** | 记忆越多越容易推荐「上次那个」 | 近 7 天重复项降权 0.28 |
| **隐私** | 档案是极敏感数据 | 本地优先、可导出、不上传第三方；LLM 调用前脱敏（待做） |
| **规则引擎天花板** | 词典覆盖不到的表达会漏 | 意图置信度低于 0.5 时主动反问 |
| **过度拟合** | 一次极端记录改变长期偏好 | 冲突队列 + 置信度衰减 |
